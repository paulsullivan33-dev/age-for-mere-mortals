# Writing criteria for this guide

Every "for Mere Mortals" guide is written to the same nine-point
standard, so a reader who trusts one can trust the rest. Here it
is, with the verification notes for this particular guide below.

1. **Fix it first.** Reader outcomes lead, not action items: each
   chapter opens by naming the outcome it delivers, shows a check
   the reader can run to confirm they got it, and a reasonable
   reader finishes able to state what was done, what it means,
   and what to try next.
2. **Plain language.** Short sentences, everyday vocabulary,
   technical terms defined on first use. No slang, and no
   idioms that only make sense in one country — the reader may
   be translating as they go.
3. **No dead ends.** A guide never tells the reader to do
   something it cannot show them how to verify. Every claim a
   reader relies on — an install, a command, an output — is
   something this guide demonstrates or clearly labels
   documented-only below.
4. **Live-verified where it matters.** Procedures are run for
   real in the guide's lab wherever the build machine allows it,
   and the transcripts kept in the repository are the evidence.
   What could not be run is listed honestly below, never
   presented as if it had been.
5. **General audiences.** Nothing in this guide — examples,
   fixtures, names, addresses — is modelled on any particular
   reader or author's real life, network, or organisations.
   The lab's files are the lab encrypting to itself.
6. **Standalone.** A reader needs this guide, its lab, and
   nothing else. Where another guide would genuinely help, it
   is pointed to once, by name, and the chapter still completes
   without it.
7. **Honest about limits.** Chapter 15 names what the tool
   cannot do: signatures, key discovery, hiding a locked
   file's size and recipient count, recovering a lost key's
   files, and stopping a recipient from copying what they
   lawfully opened.
8. **The ethics rule is in the text, early.** Chapter 1 and the
   README state the rules plainly — *encrypt your own files;
   keep your identity like a house key; a lost identity means
   lost files* — before any procedure depends on them, and
   later chapters point back to them where the tooling would
   make crossing the line easy.
9. **Builds clean.** The site builds with MkDocs in strict mode
   with no warnings, and a fresh reader following the chapters
   in order reaches the stated outcome of each.

## Verification notes for this guide

The build machine is a small Ubuntu Linux sandbox. age
**1.3.2** was run from the official release archive
(`age-v1.3.2-linux-amd64.tar.gz`) unpacked into a folder — the
machine's package sources did not carry age, so the packaged
routes in chapter 3 are described from the project's
documentation and only the release route was executed. All
transcripts live in `age-lab/transcripts/`. Every key in them
was generated for the lab and is worthless.

Run for real, with transcripts as evidence:

- Version and tool inventory of the release build (t00).
- Key generation; the identity file's exact three-line shape,
  public key as comment (t01).
- First encryption and the byte-for-byte round trip; the
  header's first bytes showing the format line and the X25519
  stanza (t02).
- Armored encryption and its round trip (t03).
- `age-inspect` on a binary and an armored file — stanza
  types, size breakdown, armor overhead (t04).
- Passphrase mode: a correct passphrase round trip, and a
  deliberately wrong one refused with `incorrect passphrase`,
  exit 1, no output file written (t05).
- Two recipients on one file, opened as each holder in turn,
  both round trips verified (t06).
- A recipients file with comments, locked with `-R`, opened
  by a member (t07).
- A throwaway SSH Ed25519 key pair: its public line as
  recipient, its private half as identity, round trip
  verified (t08).
- The deliberate wrong-key failure: `no identity matched any
  of the recipients`, exit 1, nothing written (t09).
- The autogenerated passphrase: age invents ten words, prints
  them once, and the file opens with exactly them (t10).
- `age-keygen -y` converting an identity back to its
  recipient; a sha256-verified decryption streamed through
  stdout; a tar archive piped through age in both directions
  (t11).
- A post-quantum hybrid key pair (`age-keygen -pq`): its
  round trip, and `age-inspect` confirming the
  `mlkem768x25519` stanza and the larger header (t12).
- Two scripting facts checked because the text relies on
  them: age *does* overwrite an existing `-o` target without
  warning (chapter 11 says so, correcting an early draft of
  this guide which claimed otherwise), and an identity can be
  supplied on standard input with `-i -` (t13).

Documented only — described from the project's and the
plugins' documentation, not run, and the text does not claim
otherwise:

- The package-manager installs of chapter 3 other than the
  official release route actually used, and building from
  source.
- RSA SSH keys as recipients (Ed25519 was run end to end).
- The hardware-key plugins of chapter 12 —
  `age-plugin-yubikey` and `age-plugin-fido2`. The lab had no
  security key. The plugins named as shipped in the release
  archive (`age-plugin-batchpass`, `age-plugin-tag`,
  `age-plugin-pq`) are evidenced by transcript t00's folder
  listing only.
- The comparison tools in chapter 14 are characterised, not
  benchmarked.

Fixtures are this guide's own and deliberately generic: a
one-line note about a backup drive, a two-line work rota with
invented names, and keys generated for the lab alone. Several
keys stand in for team members and are labelled as the lab
"playing" those parts in the transcripts. No example is
modelled on any real person, network, service or
organisation.
